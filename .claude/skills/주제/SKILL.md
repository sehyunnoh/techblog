# /주제: 오늘 쓸 글 주제 리서치

현재 시점(오늘 날짜 기준)에 맞는 포스트 주제 후보를 조사해서 제안한다. 글을 쓰는 것이 아니라 **제안까지만** 한다. 사용자가 고르면 그때 글을 쓴다.

응답은 한국어로 한다. 기술 용어는 원문 그대로 둔다. 시작할 때 `date`로 오늘 날짜를 확인하고, 이미 오늘 발행한 포스트가 있는지 `src/content/blog/`의 최신 `pubDate`를 확인한다. 하루 1편 제한이므로 오늘 이미 발행했다면 그 사실을 먼저 알리고 "내일 글 후보"로 제안한다.

## 1. 지켜야 할 제약

- 글이 영어로 발행되는 블로그다. 후보는 **공개 데이터를 직접 재계산해서 주장을 검증하는 형식**(숫자가 맞는지 확인하는 글)에 맞아야 한다. 프로젝트 `CLAUDE.md`의 Editorial rules를 따른다.
- 재현에 30분 넘게 걸리거나 1GB 넘게 설치해야 하는 주제는 제안하지 않는다. (예: 하루 3.5GB짜리 아카이브를 받아야 하는 주제는 탈락.)
- 글은 초중급 독자 대상이다. 처음 나오는 용어는 설명할 수 있는 주제를 우선한다.
- 이미 쓴 주제와 겹치지 않게 한다. `src/content/blog/`, `src/content/guides/`의 파일명과 제목을 훑어 비슷한 글이 있는지 확인한다. 로컬 `topics.md`(gitignored, 있으면)의 기록과 탈락 후보도 확인한다.
- 모든 주장은 확인 가능한 출처가 있어야 한다. GeekNews, 요약기의 숫자, 저장소 README의 자기 홍보 숫자는 출처가 아니라 단서다. 원문과 저장소 페이지에서 다시 확인한다.

## 2. 조사 순서

가능한 것은 한 메시지에서 병렬로 실행한다.

1. **Hacker News 1~2페이지:** WebFetch로 `https://news.ycombinator.com/`와 `https://news.ycombinator.com/?p=2`. 순위, 제목, 도메인, 점수, 댓글 수, item id를 표로 받는다.
2. **GitHub trending(일간):** WebFetch로 `https://github.com/trending?since=daily`. 요약기가 행을 중복하거나 순위를 틀린 적이 있으니, 후보로 삼을 저장소는 저장소 페이지나 `gh api repos/<owner>/<name>`으로 별 수를 다시 확인한다.
3. **GeekNews (https://news.hada.io/):** WebFetch는 ECONNRESET, curl은 403이다. **Orca 내장 브라우저**로 읽는다(`ORCA_WORKTREE_ID`가 설정돼 있을 때, `orca-cli` 스킬 사용).
   - `orca tab create --url https://news.hada.io/ --json`으로 열고 `browserPageId`를 얻는다.
   - 잠깐 기다린 뒤 `orca exec --page <id> --command "read"`로 읽는다.
   - 다 읽으면 `orca tab close --page <id>`로 탭을 닫는다.
   - 대부분 영어 원문의 번역 큐레이션이다. 후보가 되면 원문 출처를 찾아 그쪽을 인용한다. GeekNews 반응(포인트)은 한국 독자의 목록 신호일 뿐 영어권 수요 지표가 아니다.
4. **웹 검색:** WebSearch로 오늘 주목받는 릴리스, 사건, 논문, 장애, 가격 변경을 확인한다. 검색어에 이번 달을 넣는다. 위 목록에서 후보 하나를 골라 그에 대한 원문과 반론을 찾는 용도로도 쓴다.
5. **Umami (읽기 전용):** `cloud.umami.is`의 "lleg's study" 사이트. 웹사이트 id는 `66ef0eef-0524-43fe-bf94-94115299b721`이다.
   - Orca 브라우저에서 `https://cloud.umami.is/analytics/us/websites/66ef0eef-0524-43fe-bf94-94115299b721?date=7day`를 열고 `read`한다. `orca tab list --json`으로 이미 열린 Umami 탭이 있는지 먼저 본다.
   - 로그인이 풀려 있으면 **사용자가 직접 로그인**하게 안내한다. 비밀번호를 채팅으로 요구하지 않는다. 수정과 삭제는 하지 않는다.
   - 날짜와 필터는 URL로 준다: `?date=7day`, `?date=0month`, `?date=range%3A<startMs>%3A<endMs>%3Aall`, `&path=eq.%2Fposts%2F<slug>%2F`, `&referrer=eq.google.com`. `startAt/endAt`은 무시된다. 펼친 "More" 목록은 읽히지 않을 수 있다.
   - 볼 것: 최근 7일, 이번 달 방문자와 이탈률, google.com 유입, 어떤 글이 읽혔는지, 이탈률 97%에 6초면 "클릭만 되고 읽히지 않은 것". 페이지 표가 전부 0으로 읽히면 로딩 문제일 수 있으니 쓰지 않고 그 사실을 적는다.
   - 방문자가 월 수백 명 수준이라 약한 근거다. 한 번의 링크 급증을 추세로 해석하지 않는다. 지금까지의 관찰: 제품명+버전형 주제가 Google에 닿고, Go 글은 Go Weekly로 클릭은 오지만 거의 읽히지 않으며, 공유된 글(LinkedIn, Substack)이 오래 읽힌다.
   - 탭을 닫거나 로그아웃은 사용자가 정한다. 작업 끝에 Umami 탭이 로그인된 상태로 남아 있다고 알린다.

한 소스가 실패하면 실패한 사실을 보고하고 나머지로 진행한다. 실패를 숨기거나 추측으로 메우지 않는다.

## 3. 후보 검증 (제안하기 전에 최소한)

후보 3개 각각에 대해 "재계산 가능성"을 실제로 한 번 찔러 본다. 보고서에는 **확인한 것**과 **아직 확인하지 못한 것**을 구분해서 적는다.

- 데이터 출처가 공개이고 접근 가능한가? (API 한두 번 호출, 파일 크기 확인, `gh api` 등)
- 규모가 제한 안에 들어오는가? 다운로드 크기를 `Content-Length`나 저장소 메타데이터로 확인한다.
- 기사나 글이 근거라면 본문을 읽었는지, 요약만 봤는지 밝힌다.

## 4. 출력 형식

한국어로, 다음 순서로 짧게 쓴다.

1. **오늘 본 것:** 소스별 한두 줄(HN, GitHub trending, GeekNews, Umami). 실패한 소스가 있으면 여기에 적는다.
2. **후보 3개:** 각각 (a) 제목 후보, (b) 근거(링크 가능한 출처와 직접 확인한 숫자), (c) 재계산 내용(무엇을 어떻게 셀지), (d) 비용(분, 다운로드 크기), (e) 약점과 확인하지 못한 점. 제품명+버전형이면 Google 유입 가능성도 한 줄.
3. **추천 1개와 이유.** 두 번째로 낫다고 보는 것과 갈리는 기준(예: Google 유입을 노리면 B)을 한 줄로 쓴다.
4. 맨 끝에 "어느 쪽으로 쓸까요?"로 묻는다. 사용자가 고르기 전에는 글을 쓰거나 파일을 만들지 않는다.

탈락시킨 후보가 있으면 이유와 함께 한 줄씩 적는다(예: 자료가 1GB 초과, 근거가 약함). 사용자가 후보를 고르면 `topics.md`가 있는 경우 그날의 기록(선택한 것과 탈락 사유)을 추가한다.
