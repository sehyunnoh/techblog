A normal `git clone` downloads every version of every file the repository has ever had. For a small project that is fine. For a big one it can be the slowest step of your build, and a few git features exist to avoid it. They are easy to turn on and easy to misread, because each one removes a different thing, and some of them move the cost to a later command that you do not expect to be slow.

This guide walks through them in the order you would use them: clone a slice, look at what you got, fetch more when you need it, and see which commands get expensive. Every command was run on `rust-lang/rust`, which has 63,674 tracked paths and more than 340,000 commits, using git 2.55.0 on Windows 11.[^1] Each step lists the time and how much the object store (`.git/objects`) grew. I also wrote a [separate post](/posts/git-naive-fetch-600-pb-vs-stock-git) with the whole-clone comparison. This page is about doing it by hand and what surprised me along the way.

## The words you need

A **commit** is a snapshot of the project with a message and a parent. A **tree** is a directory listing. A **blob** is the contents of one file. A repository is mostly blobs, plus the trees and commits that connect them. The server you clone from is the **remote**.

Three features cut the download, and they cut different things:

| Feature | Flag | What it leaves out |
|---|---|---|
| Shallow clone | `--depth 1` | Everything except the latest commit's history[^2] |
| Partial clone | `--filter=blob:none` | File contents (blobs) until something needs them[^2] |
| Treeless clone | `--filter=tree:0` | Directory listings (trees) too, until needed[^3] |
| Sparse checkout | `--sparse` | Files in your working directory only, not the download[^4] |

A partial clone works because the remote stays on call: git remembers it as a **promisor remote**, a server that promised to supply the missing objects later on demand.[^2] You will see this in step 2.

## Step 1: clone a slice

The smallest useful clone combines three flags: only the latest commit, no file contents until needed, and a working directory with only the top-level files at first. Then you name the directory you actually want.

```bash
git clone --depth 1 --filter=blob:none --sparse https://github.com/rust-lang/rust.git rust
cd rust
git sparse-checkout set library/core
```

On Windows, add `-c core.longpaths=true` to the clone if the repository has very long paths. I come back to that in the pitfalls.

Measured: 3.8 seconds, 3.9 MiB in the object store, and 356 files in the working directory. The full repository has 63,674 tracked paths.[^1] `--sparse` starts git in **cone mode**, where you list directories and everything under them is included, along with the files directly in the top-level directory.[^4]

## Step 2: check what you actually got

Do not trust that the flags worked. Three quick checks:

```bash
git config --get-regexp '^(remote\.origin\.(promisor|partialclonefilter)|core\.sparsecheckout)'
git rev-parse --is-shallow-repository
git sparse-checkout list
```

My output:

```text
remote.origin.promisor true
remote.origin.partialclonefilter blob:none
core.sparsecheckout true
core.sparsecheckoutcone true
shallow: true, sparse list: library/core
```

`promisor true` and the filter line confirm the partial clone. Then compare counts: `git ls-files | wc -l` reports all 63,674 tracked paths while only 356 files exist on disk. That gap is how sparse checkout is supposed to look, so a mismatch is not a bug by itself. It becomes one if you expected the files to be there, which is how I found a different problem later.

## Step 3: see the holes

Git can list the objects it knows about but does not have:

```bash
git rev-list --objects --missing=print HEAD | grep -c '^?'
```

It printed 61,703 missing blobs and took 12.5 seconds. Those are the file contents git promised to fetch when needed, about 97% of the files at the tip.

## Step 4: fetch one file on demand

Reading a file outside your sparse set triggers a download of just that file:

```bash
git show HEAD:compiler/rustc_borrowck/src/lib.rs | wc -l
```

That printed 2,781 lines in 0.7 seconds and grew the object store by about 0.1 MiB. This is the promisor remote at work, and it is why a partial clone feels normal until the network is slow, because every missing object costs a round trip.

## Step 5: add more directories later

```bash
git sparse-checkout add library/alloc
```

0.9 seconds, 0.4 MiB, and the working directory went from 356 to 453 files. `add` grows the set. `set` replaces it with exactly the directories you list, and the documentation notes that running `set` again changes your selection.[^4] To go back to everything:

```bash
git sparse-checkout disable
```

That one is not free, as step 9 shows.

## Step 6: you need a bit of history

A shallow clone has one commit. You can deepen it two ways, and they do not behave alike:

```bash
git fetch --deepen=5
git fetch --shallow-since=2026-10-11
```

`--deepen` counts commits from the current boundary, and `--shallow-since` takes everything after a date.[^5] Here is what happened on this repository:

| Command | Commits afterwards | Added to object store |
|---|---|---|
| `--deepen=1` | 3 | 0.4 MiB |
| then `--deepen=5` | 50 | 1.2 MiB |
| `--shallow-since` three days back (separate copy) | 106 | 1.5 MiB |

Asking for one more commit gave me three, and asking for five more took me from 3 to 50. The depth is counted along every branch of history, and this project merges constantly, so one step back reaches several parents at once. If you want to predict how much history you will get, use a date, not a number.

## Step 7: history commands, and the one that costs more than a full clone

Sparse checkout and `--depth 1` hide how heavy history commands can get. To see that, I made two history-complete clones without checking out any files and ran the same question on each: the last 20 commits that touched `library/core/src/option.rs`.

```bash
git clone --filter=blob:none --no-checkout https://github.com/rust-lang/rust.git bl
git -C bl log -n 20 --oneline -- library/core/src/option.rs

git clone --filter=tree:0 --no-checkout https://github.com/rust-lang/rust.git tr
git -C tr log -n 20 --oneline -- library/core/src/option.rs
```

The treeless clone looked cheap at 143.8 MiB and then downloaded about 1.6 GB while answering a question that only needed 20 results. A full clone of this repository is about 1.1 GB.[^6] GitHub's own guidance says why: with `tree:0`, a path-limited `git log` has to fetch the root tree of almost every commit it walks, and it recommends treeless clones for automated builds, not for developers.[^7] Blame in a blobless clone has a different problem. It fetched only 35 MiB, yet took about nine minutes. Small bytes and a long time point at many round trips to the server, not bulk transfer, though I did not trace the requests to confirm it.

The rule I take from this is simple. Blobless is a reasonable default for a person. Treeless is only for jobs that never ask about history.

## Step 8: when you change your mind

Turn the sparse checkout off in the small clone from step 1:

```bash
git sparse-checkout disable
```

118.3 seconds, the object store grew from 6.0 to 57.3 MiB, and the working directory went from 453 to 63,662 files. In other words, switching to "I need everything" costs about what a shallow clone costs. Much of the time is probably spent writing 63,000 files: in my earlier benchmark, a clone that downloaded the same amount took 15 seconds when only 356 files were written. If the filter itself was the wrong choice, the documentation describes `git fetch --refetch`, which re-downloads all objects as a fresh clone would and can reapply a changed filter.[^5] I did not test it.

## Pitfalls

**Windows long paths.** This repository has paths over 260 characters. In my first attempt the checkout stopped at 17% with `Filename too long`, yet the clone still reported success, and I published wrong working-directory numbers because of it. If you clone on Windows, pass `-c core.longpaths=true` and compare `git ls-files | wc -l` with the number of files on disk afterward. I wrote up that mistake in a correction on the [earlier post](/posts/git-naive-fetch-600-pb-vs-stock-git).

**Sparse checkout does not save bandwidth by itself.** It changes the working directory only. Pair it with a filter if you want a smaller download.[^4]

**Shallow clones do not stay cheap.** GitHub's guide warns against fetching into a shallow clone because it can pull an almost-full history.[^7] In my related measurement, an update into a shallow clone cost about as much as cloning again.

**Missing objects need the server.** Anything that touches an object you do not have is a network request. That is the design, and it means a partial clone can slow down or stall on a bad connection, a firewall or a server that stopped serving the repository. I did not test an offline case.

**Your server has to support it.** Partial clone asks the server to send a subset of objects.[^2] I tested only against GitHub. A self-hosted server may handle it differently.

## What I did not test

One repository, one operating system, one git version, and one server. Times are single runs on my connection and include slow file creation on Windows. I did not measure `git pull`, `git diff`, `git checkout` of another branch, `--refetch`, `--unshallow`, or blame on the treeless clone (the log alone took 14 minutes). The `--deepen` numbers depend on this repository's merge-heavy history and will differ on yours. Run the script below on your own repository before trusting any of my ratios.
