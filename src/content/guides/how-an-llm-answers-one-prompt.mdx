A large language model does one thing: given some text, it picks the next small piece of text. Everything you see, a paragraph, a code review, a translation, comes from running that step over and over, each time with the previous output added to the input. This guide follows a single request through that loop, one stage at a time, and puts a measurement on each stage so the explanations are not just assertions.

Two honest limits first. The numbers about text come from real tokenizers. The numbers about speed come from a small model I wrote in NumPy with random weights, so the text it produces is noise. It does the same kind of work per token as a real model, just at a much smaller scale, and every timing here is a statement about that toy on my laptop, not about any commercial model. Where a real model's published settings matter, I use them, and I say so.

## Step 1: text becomes integers

The model never sees letters. A **tokenizer** cuts the text into pieces called **tokens**, each with a fixed integer ID, and the model works on those IDs. Most tokenizers use **byte pair encoding** (BPE), which starts from single bytes and repeatedly merges the pairs that occur most often in a training corpus, until it has a vocabulary of a chosen size.[^1] Common words end up as one token. Rare words are spelled out in fragments.

I ran OpenAI's open-source `tiktoken` library on a few strings with three of its vocabularies.[^2] The English sentence and its Korean translation carry the same meaning:

| Text | Characters | GPT-2 (50k vocab) | cl100k (100k) | o200k (200k) |
|---|---|---|---|---|
| English sentence | 160 | 35 | 35 | 35 |
| Same sentence in Korean | 74 | 157 | 72 | 46 |
| 4 lines of Python | 50 | 26 | 20 | 20 |
| 40 digits | 40 | 16 | 14 | 14 |

Two things are worth taking from this. First, token counts depend on which tokenizer a model uses, so "how many tokens is this" has no answer without naming one. The same Korean sentence costs 157 tokens in the oldest vocabulary and 46 in the newest, while the English one does not move. Second, an unfamiliar script is expensive: in cl100k, the Korean sentence needs twice the tokens of the English one even though it has less than half the characters.

The pieces can be odd. In cl100k, the word `strawberry` splits as `str`, `aw`, `berry`, which is one reason models have stumbled on counting its letters: the model never sees them. And the five-syllable greeting 안녕하세요 comes out as five tokens, some of which are partial characters (a Korean syllable takes three bytes in UTF-8, and cl100k sometimes cuts between them). In o200k the same greeting is two tokens, and whole syllables stay together.

## Step 2: through the layers

Each token ID is looked up in a table to get a vector of a few thousand numbers, its **embedding**. That vector then goes through a stack of identical **layers**. A layer does two things: an **attention** step, where the token gathers information from earlier tokens, and a feed-forward step, which transforms each token's vector on its own.[^3] The last layer's output for the final position is multiplied by one more matrix to give the **logits**, a score for every token in the vocabulary.

To make the sizes concrete, here is a real configuration. Qwen2.5-7B publishes 28 layers, a hidden size of 3,584, and a vocabulary of 152,064 tokens in its `config.json`.[^4] Adding up the matrices from those numbers gives about 7.6 billion parameters, which at 2 bytes each is roughly 15.2 GB of weights. Keep that number in mind. Every token generated has to pull most of those 15 GB through the processor.

My toy has 12 layers, a hidden size of 768 and a 32,000-token vocabulary: 134.9 million parameters, or 540 MB in 32-bit floats.[^5]

## Step 3: attention, and why the KV cache exists

Attention is where a token looks back. For every token, each layer computes a **query** ("what am I looking for"), a **key** ("what do I contain") and a **value** ("what do I pass on"). A token's query is compared against the keys of all earlier tokens, and the result weights a mix of their values. That is how the word "it" can pull in information from a noun ten tokens earlier.

Notice what this means for generating text. When the model adds token 513, it needs the keys and values of tokens 1 to 512 in every layer. Those do not change, because earlier tokens never look at later ones. So a real implementation keeps them in memory after computing them once. That stored pile is the **KV cache**.

I measured the difference with the toy. I gave it a 512-token prompt, asked for 40 more tokens, and generated them two ways: recomputing the whole sequence at every step, and using the cache. Both produced exactly the same 40 tokens, which is the check that the cache is a pure optimization.

| Method | Time per new token (median of 10) |
|---|---|
| No cache, whole sequence every step | 957 to 1,234 ms |
| With KV cache | 15 to 22 ms |

That is roughly 50 times, in line with the amount of repeated work. Without the cache, each new token costs about as much as reading the entire prompt again. Four runs gave the ranges above.

The cache has a price, and it is paid in memory. For each token, each layer stores one key and one value vector per KV head:

> bytes per token = 2 (key and value) × layers × KV heads × head size × bytes per number

Qwen2.5-7B has 28 layers, 4 KV heads of size 128, and stores numbers in 2 bytes, so each token adds 56 KiB.[^4] Most modern models share each KV head across several query heads, a trick called **grouped-query attention**, to shrink this.[^6] Qwen uses 28 query heads but only 4 KV heads. If every head kept its own, the cache would be seven times bigger:

| Context length | Qwen2.5-7B (4 KV heads) | If it had 28 KV heads |
|---|---|---|
| 8,192 tokens | 448 MiB | 3.06 GiB |
| 32,768 tokens | 1.75 GiB | 12.25 GiB |
| 131,072 tokens | 7 GiB | 49 GiB |

Those are per conversation. A server handling many conversations at once multiplies it, which is why KV cache memory, not raw compute, usually limits how many requests fit on one GPU, and why systems such as vLLM manage the cache in fixed-size pages.[^7]

## Step 4: prefill and decode are different jobs

Now the two halves of the diagram at the top. **Prefill** processes the whole prompt in one go: all 512 tokens go through the layers together as one big matrix multiplication, and the cache is filled. **Decode** then produces one token at a time, and each step feeds in just that one token.

In my toy, prefill of 512 tokens took 0.91 to 0.99 seconds, about 520 to 560 tokens per second. Decoding one token took about 18 ms, about 55 tokens per second. Prefill moves roughly ten times as many tokens per second, and the reason is visible if you vary how many tokens go through the model in a single call:

One token costs 18.6 ms and 256 tokens cost 1.8 ms each, about ten times less. The weights are the same 540 MB either way. A single-token step reads all of them to do very little arithmetic, so it is limited by how fast memory can deliver them. A batch of tokens reuses each weight many times after loading it, so it is limited by arithmetic instead. This is the "memory-bandwidth bound" statement in Apple's Muse Spark report, and I checked the same effect on raw memory reads in [an earlier post](/posts/muse-spark-four-macs-fixed-cost-per-token). The split between the two phases is the subject of [Your LLM Is Two Different Machines](/posts/llm-inference-two-machines).

My toy is not near the hardware limit. At 18.6 ms per token it moves 540 MB at about 29 GB/s, while a hand-written C loop on the same machine reached 94 GB/s in that earlier post. NumPy's small operations, Python overhead and extra copies eat the difference. Real inference engines fuse these steps into custom kernels, so treat the toy as a model of the shape of the cost, not its size.

The cache also shows up in the decode time. With the cache already holding 64, 256, 512 and 1,024 tokens, a decode step took 18.3, 19.9, 21.0 and 23.9 ms (median of three runs). Each new token has to read the whole cache as well as the weights, so decoding gets slower as a conversation grows, slowly in this toy because its cache is small next to its weights. For a long-context model whose cache is a large fraction of its weights, the effect is larger.

## Step 5: picking the next token

The logits are raw scores. A function called **softmax** turns them into probabilities that add up to 1. The simplest rule, **greedy decoding**, takes the highest one, and my measurements used it so that the cached and uncached runs could be compared exactly.

Chat products usually sample instead. **Temperature** divides the logits before softmax, so a low value sharpens the distribution toward the top choice and a high value flattens it. **Top-p** (also called nucleus sampling) keeps only the smallest set of tokens whose probabilities add up to p and samples from those, which cuts off the long tail of unlikely tokens.[^8] Neither changes how much computation a step costs. They only change which token is picked from the scores that were already computed.

The picked token is appended to the text, and the loop in the diagram goes round again.

## What this explains

Several everyday observations are direct consequences of the steps above:

- **A long prompt delays the first word, a long answer takes a long time to finish.** The first is prefill, which scales with prompt length. The second is decode, which costs roughly the same per token, plus a slow rise as the context grows.
- **Many providers charge more for output tokens than for input tokens.** Input goes through prefill at high throughput. Output runs the slow one-token-at-a-time loop. I have not verified any provider's reasons, but the cost structure matches the measurements.
- **Long context eats memory, not just time.** The table of KV cache sizes is why a model that fits in memory at 8,000 tokens can fail at 128,000.
- **Non-English text costs more.** In cl100k, the Korean sentence needed twice the tokens, which means twice the prefill work, twice the cache, and twice the per-token price for the same meaning.
- **Batching many users together is how servers stay efficient.** The chart is the reason: reading the weights once and serving many sequences at once makes each token cheaper.

## Limits of these measurements

The speed numbers are one machine (a Core Ultra 7 258V laptop on Windows 11), one script, and one small model with random weights in 32-bit floats. They show how cost is shaped, not what any production model delivers. Real systems use 8-bit or 4-bit weights, fused attention kernels, paged caches and GPUs with memory many times faster than this laptop's. The tokenizer counts are exact for the three vocabularies named, but other model families use their own, and I did not measure them. The KV cache sizes come from arithmetic on a published configuration, not from watching a real server's memory.
