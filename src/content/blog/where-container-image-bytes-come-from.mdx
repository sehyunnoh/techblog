An image with numpy, pandas and requests on top of `python:3.13-slim` takes 91 MB to pull and 272 MB on disk. The slim base alone is 43 MB to pull, and `docker image ls` printed 176 MB for it. Three numbers for one image is already a hint that "image size" is not one thing.

I wanted to know where the bytes actually sit, so I unpacked a set of Python images layer by layer and then rebuilt them with the habits that tutorials recommend, and a few that they skip. Some of what I expected held. Some did not. In particular, I assumed my own code and Python itself would be a large part of the image, and I assumed that deleting a cache in a later `RUN` would give the bytes back.

## Background: layers and the three sizes

A container image is a stack of **layers**. Each `RUN`, `COPY` or `ADD` in a Dockerfile produces one, and each layer is stored as a compressed tar archive of the files that step added or changed. Layers are read-only. When a later layer deletes a file, it does not touch the earlier layer. The OCI image specification records the deletion as a **whiteout**, an empty file named `.wh.` plus the deleted name, which hides the file from the merged view.[^1] The bytes stay where they were.

That gives three sizes worth separating:

- **Registry size**: the sum of the compressed layers. This is what a pull downloads and a registry stores.
- **Unpacked size**: the files a running container sees after all layers are merged, with whiteouts applied.
- **What Docker prints**: depends on the engine. More on this below.

I measured all three with a small script that runs `docker save` and reads every layer of the archive.[^7]

My setup, so you can judge what transfers: Docker 28.0.4 on Docker Desktop for Windows 11 (the engine runs in a Linux VM, `linux/amd64`), Python 3.13.17 on Debian trixie, numpy 2.5.4, pandas 3.1.0. Every Dockerfile variant was built with `--no-cache`. Build sizes were identical across repeated runs, which is expected for the same inputs.

The gap between the two series is nearly constant. Python slim unpacks to 2.66 times its compressed size, the full image to 2.67 times, the Alpine one to 2.69 times. For a quick estimate, an image is about 2.7 times bigger on disk than on the wire.

Then there is the number Docker itself prints. For `python:3.13-slim` on my machine, `docker image inspect` reports 43.1 MB, which is the compressed size, and `docker image ls` reports 176 MB. Docker's documentation explains the second one: the containerd image store keeps the compressed layers and the extracted layers, while the older storage drivers kept only the extracted ones.[^2] Compressed plus unpacked is 157.9 MB, so the printed figure is about 12% higher than that sum. I did not track down the remainder. The practical point is that an `ls` size from a machine with the containerd store and one from a machine without it are not comparable, and neither one is what your registry bill is based on.

I grouped every file in the merged filesystem by path. The Python bucket is `/usr/local`, where the official images install the interpreter, the standard library and `site-packages`.

Python is 74% of the Alpine image, 28% of the slim one and 6.5% of the full one. The rest is the operating system underneath. In the full image the toolchain (compilers, headers, `libexec`) alone is 180 MB, because it is built on `buildpack-deps`, an image meant for compiling things.

One number in that chart looks wrong at first. The Python bucket is 32.4 MB in slim and 71.3 MB in full, though both ship Python 3.13.17. The difference is `libpython3.13.so` (28.8 MB in full, 5.2 MB in slim) and the compiled extension modules in `lib-dynload` (21.0 MB against 5.7 MB). I checked the full image with `file`, and it reports `with debug_info, not stripped`. Running `strip --strip-unneeded` on that library gave a file of exactly 5,239,800 bytes, the same size as the one in the slim image.

The official Dockerfiles explain it. The slim one adds `-Wl,--strip-all` to the linker flags, and the full one does not.[^3] So the 38.9 MB difference between the two Python buckets is the gap between an unstripped and a stripped build of the same files. I verified that for `libpython` directly and took the same cause for the extension modules from the Dockerfiles, not from a separate test. It is not a flaw in either image. It is a default you inherit when you pick the tag, and you are unlikely to attach a debugger to the interpreter inside a container.

## Deleting in a later layer does not give bytes back

Here is the layer stack for the most common mistake. You install packages with pip, which writes a download cache under `/root/.cache/pip`, and then you clean it up in the next instruction.

The `rm` in the next layer fixed the unpacked size (303.4 to 272.2 MB) and changed the registry size by exactly nothing. Anyone pulling that image still downloads the 30.6 MB cache. Doing the removal in the same `RUN` as the install, or skipping the cache with `--no-cache-dir`, saves it on both measures. A BuildKit cache mount (`RUN --mount=type=cache,target=/root/.cache/pip`) also produced the smaller image. It has the extra benefit of keeping the cache between builds on your machine, which matters because pip's own documentation warns against `--no-cache-dir` unless something higher up, such as layer caching in a container build, already covers it.[^4]

The same rule hurts in a less obvious place. I copied 40 MB of data into `/app/data` and then ran `chown -R 1000:1000 /app` as a separate step. Changing ownership counts as a modification, so the file system has to store every file again in the new layer. The registry size went from 83.1 to 123.1 MB, exactly 40.0 MB more, and the unpacked size did not move. `COPY --chown=1000:1000` set the same ownership at no cost, at 83.1 MB.

## What is inside your dependencies

With the base image and the layer rules covered, I looked at what pip puts into `site-packages`. The three packages add 157 MB unpacked. Most of that is pandas at 76.1 MB, numpy at 40.5 MB, and `numpy.libs`, the shared libraries bundled with the numpy wheel, at 27.5 MB. Inside pandas, 38.6 MB is `pandas/tests`. Half of the pandas in this image is the pandas test suite.

I tried two common reductions and checked that each image still imported pandas and numpy and summed a small DataFrame:

| Variant | Registry (MB) | Unpacked (MB) | Cold `import pandas` (s) |
|---|---|---|---|
| Baseline, `--no-cache-dir` | 91.2 | 272.2 | 0.24 |
| `pip --no-compile` | 75.6 | 225.9 | 0.93 |
| Delete dirs named `test`/`tests` | 76.9 | 218.8 | 0.24 |
| Both | 71.3 | 203.8 | 0.92 |

Deleting the test directories removed 53.4 MB unpacked and 14.3 MB from the pull, with no change in import time. Skipping bytecode compilation (`--no-compile`) removed 46.3 MB unpacked and 15.6 MB from the pull, and it made the first import almost four times slower, from 0.24 to 0.93 seconds. The time is the median of five runs, each in a fresh container, so no `.pyc` files from a previous run could help. Python writes bytecode on first import when it can, but a container that starts, serves one request and exits never keeps it.

That makes `--no-compile` a different kind of choice from deleting tests. One costs nothing at runtime. The other trades image size for start-up time on every cold start, so it is a poor deal for serverless or autoscaled containers and a fine one for a service that starts once a day.

## Compilers, Alpine and the build context

The last group is about what you leave behind from building. I used `psycopg2`, the PostgreSQL driver, because installing it from source needs a C compiler and the PostgreSQL client headers.

| Variant | Registry (MB) | Unpacked (MB) |
|---|---|---|
| Compiler and `libpq-dev` left in | 143.7 | 361.6 |
| Same, apt package lists removed in the same `RUN` | 127.0 | 340.0 |
| Multi-stage: build a wheel, install it in a clean slim image | 48.9 | 127.4 |
| `psycopg2-binary` wheel | 51.0 | 135.0 |

The multi-stage build cut 94.8 MB from the pull compared with leaving the toolchain in, and it was 2.1 MB smaller than the prebuilt binary wheel, which bundles its own copy of the client library.[^6] Removing the apt lists alone was worth 16.7 MB. Two small notes from getting this to build: `--no-install-recommends` left out `libc6-dev`, and the compile failed on a missing `assert.h` until I added it. In the multi-stage version, the final image installs `libpq5`, the runtime library, and nothing else.

Alpine has a reputation for breaking Python packages with native code, because it uses musl instead of glibc and older wheels were built for glibc only. I expected the gap to Alpine to disappear once numpy and pandas went in. It did not. With the same three packages, the Alpine image was 68.0 MB to pull against 91.2 MB for slim, and 212.7 MB unpacked against 272.2 MB. The bare base gap had been 26.2 MB to pull and 69.4 MB unpacked, so the lead shrank a little but stayed. The reason is that both packages now publish `musllinux` wheels, which I confirmed by listing what pip downloaded (`numpy-2.5.4-cp313-cp313-musllinux_1_2_x86_64.whl` and a matching pandas file). The musllinux tag is defined in PEP 656.[^5] Nothing was compiled.

The biggest single mistake came from the plainest instruction. I used this blog's own repository as the build context and ran `COPY . /app` with no ignore file. The image grew from 43.7 MB to 214.7 MB to pull, and from 116.5 MB to 578.6 MB unpacked, most of it a 472 MB `node_modules` folder. The build took 88 seconds instead of 1.3, because the whole directory had to be sent to the builder first. A `.dockerignore` listing `node_modules`, `.git` and the build output brought it back.[^6] Besides size, `COPY . .` also puts any local notes or config files you forgot about into the image.

## Trade-offs and what I did not test

- **One machine, one architecture.** Everything is `linux/amd64` on Docker Desktop. Apt and PyPI contents change over time, so the exact megabytes will drift, though the pattern should not.
- **Deleting `tests` directories is a blunt tool.** I removed every directory named `test` or `tests` under `site-packages` and checked that numpy and pandas still worked. A package that loads data from a folder with such a name would break, and I did not check any beyond these two.
- **Alpine's other differences are untested.** I measured size and that the packages import. I did not measure speed or behaviour differences from musl, which are the usual reasons people leave Alpine.
- **Cold-start numbers are from a laptop** with other things running. The median of five was stable across two full runs (0.24 and 0.25 seconds for the baseline, 0.93 and 0.87 for `--no-compile`), but the exact values are not portable.
- **Registry size is compressed with Docker's default settings.** A registry or a different builder could compress differently.
- **I did not measure pull time.** Bytes are a proxy. Layer reuse across images matters too, and a shared base layer is only downloaded once per machine.

## Takeaways

- Check which size you are looking at. Registry size, unpacked size and what `docker image ls` prints differ by a factor of about 2.7 or more, and the last depends on the storage backend.
- The bulk of a Python image is usually the operating system beneath it. Choosing the base (full, slim, Alpine) moves more bytes than anything you write in your own layers.
- A file removed in a later layer stays in the pull. Clean up in the same instruction, use `--chown` on `COPY`, and send build tools to a throwaway stage.
- Look inside your dependencies before trusting them to be lean. Half of pandas here was its own tests, and skipping bytecode saved 46 MB at the cost of a four-fold slower first import.
- Write a `.dockerignore` before the first `COPY . .`. It was the largest single difference I measured.
