On September 7, Docker shipped version 0.42.0 of Sandboxes — the product that runs each AI coding agent in its own microVM instead of a container.[^1] The release notes list two critical fixes: CVE-2026-77179, CVSS 9.4, and CVE-2026-79994, CVSS 8.7.[^1] They were found independently, by two different security researchers, roughly three weeks apart, using unrelated techniques.[^2][^3] And they broke the isolation boundary in the exact same place: the one spot where a sandboxed agent is allowed to talk back to the host.

[A previous post on this blog](/posts/six-agents-twenty-four-kilobytes) measured what container isolation actually costs a fleet of agents — and found that the bind mount making it *convenient* quietly hands the sharing back, 465 MB at a time. Docker Sandboxes is a different architecture, sold on exactly that weakness: a real hypervisor boundary, not a shared kernel with namespaces drawn around it. Two independently discovered bugs, patched in the same release, are a good test of whether the stronger boundary actually held where it mattered.

## A microVM is not a container with better manners

A container and a microVM solve isolation differently. A container shares the host's kernel; the wall around it is namespaces and cgroups — visibility rules enforced by the same kernel the host is running. A microVM has no such shared kernel. Docker's own documentation is specific about this: "every sandbox runs inside a lightweight microVM with its own Linux kernel."[^4] The sandboxed agent cannot see the host's process table, cannot see host device files, cannot exploit a namespace-confusion bug — because there is no shared namespace to confuse. Outbound network traffic is also isolated per sandbox and routed through a policy-based proxy rather than given a raw route to the host network.[^4]

That is a real, structural improvement over the container boundary measured in the earlier post. But a sandbox that can see nothing of the host is also useless to a coding agent — it needs the project's files, and it often needs specific host services. So the design adds exactly two deliberate bridges back across an otherwise sealed wall: a shared folder, so the guest can read and write project files, and a Unix-domain-socket relay, so the guest can reach a short allow-list of host sockets. Every bridge is a place where a host-side process, running with real privileges outside the VM, has to trust something the guest supplies. That is exactly where both patched bugs live.

## Bridge 1: a file handle that outlives its path

The shared folder is implemented with virtio-fs: a host-side server process speaks a FUSE-like protocol to the guest kernel over a virtio queue. The first time the guest touches a path, the server hands back a *nodeid* — a short handle the guest reuses for later operations instead of resending the full path each time, which is the whole performance point of the scheme. Security researcher Oren Yomtov, who reported CVE-2026-77179, found that on macOS the server resolves a nodeid two different ways: normally through an inode lookup, but when that lookup fails, it falls back to the path string it cached the first time it saw that nodeid — and reopens the file at that path without checking whether the path still means what it meant the first time.[^2]

The general shape of the attack, in Yomtov's own words: the guest picks a target file on the host, creates a folder and a file with the same name inside the shared workspace, keeps a handle to it open, deletes both the file and the folder, replaces the folder with a symlink pointing anywhere on the host filesystem, and then reads or writes through the still-open handle.[^2] His published proof of concept is three lines:

```bash
mkdir pv && : > pv/.canary && exec 9< pv/.canary
rm pv/.canary; rmdir pv; ln -s /Users/Shared pv
echo CONFIRMED > /proc/self/fd/9
```

CWE-59, "Improper Link Resolution Before File Access," is the classification for exactly this pattern: trusting a path across a gap in which an attacker can substitute a symlink for a real file.[^5] The fix in 0.42.0 makes the server re-verify the resolved path stays inside the shared workspace before reopening it — the check that was missing.[^1]

## Bridge 2: the same gap, in a different clock

CVE-2026-79994, reported separately by Jurre van Bergen of ThreatNotify, hits the second bridge.[^6] Docker Sandboxes' guest-to-host socket relay is meant to let the agent reach a short list of authorized Unix-domain sockets — and explicitly *not* reach dangerous ones, like the host's own Docker daemon socket or the system D-Bus.[^7] To enforce that, the relay validates a requested socket path with `stat()`, confirms it sits inside the authorized workspace, and then connects to it by that same pathname.[^8]

The bug is the gap between those two steps. A malicious guest can replace an intermediate directory in that path with a symlink in the window between the validation and the connect — a textbook time-of-check-to-time-of-use race, CWE-367 — so the host ends up connecting to an arbitrary `AF_UNIX` socket instead of the one it just checked.[^8]

Different CWE entry, different bridge, three weeks apart, two researchers who — as far as either publication says — were not working together. What they found is the same structural mistake wearing two different masks: a host process that checks a guest-supplied reference once, then trusts it again later without re-checking, while the guest controls exactly what happens in between.

## What the fix actually is

Both bugs shipped fixed in 0.42.0 on the same day.[^1] But Docker's own hardening advice for the file-sharing bridge is not "the bridge is now safe" — it's "avoid needing it." Sandboxes has a `--clone` mode in which the host repository is mounted **read-only** at a fixed path, the agent works against a private clone made inside the VM, and — per Docker's own isolation documentation — "the agent cannot modify any tracked file or any byte under `.git/`."[^4] A read-only mount structurally removes the write-back path both of these bugs needed; there is no live, writable shared folder for a stale nodeid or a swapped symlink to abuse. The safest bridge, as usual, is the one you didn't build.

## Trade-offs

**The threat model this assumes is the one the product exists for.** CVE-2026-77179's CVSS vector has `AV:L` — the attacker needs to already be executing code inside the guest.[^2] That is not a weaker bug; it is *the exact* attacker Docker Sandboxes was built to contain — a coding agent that has been prompt-injected, or that installs and runs something malicious as part of a task. A local-only attack vector is disqualifying for a lot of vulnerability classes. It is not disqualifying here, because the whole point of the product is to survive that attacker.

**Two researchers, two bridges, one release cycle is a signal about the architecture, not a coincidence about the researchers.** Both bugs are guessable from the design once you know it has exactly two deliberate crossings of the hypervisor wall, and that both crossings are implemented as "check a guest-supplied path once, act on it again later." That is a pattern worth auditing for anywhere else the same design shows up — not just in this product.

**The patch has to reach you; it does not push itself.** Docker has not reported exploitation, and CISA's assessment lists none as of publication.[^1] But 0.42.0 fixing a critical, locally-exploitable VM escape only helps a machine that has actually pulled it — this ships as a developer-run CLI/runtime update, not a server-side SaaS patch applied for you. The gap between reserving a CVE (August 20) and shipping the fix (September 7) was about eighteen days;[^1][^2] the gap between your machine and that fix depends entirely on whether you updated.

**The isolation layer changed; the shared-directory property didn't.** [The container post](/posts/six-agents-twenty-four-kilobytes) found that bind-mounting a project directory into a container hands back exactly the sharing the container's namespace wall was supposed to remove. virtio-fs sharing a directory into a microVM is the same trade at a different layer: whatever you deliberately share is, by construction, reachable from both sides. The hypervisor wall protects everything you didn't explicitly bridge. It was never going to protect the bridge itself.

## Takeaways

- **A stronger isolation technology doesn't remove the need for a boundary; it moves where the boundary has to hold.** Docker Sandboxes' hypervisor wall genuinely removes the shared-kernel attack surface a container has — and then reintroduces risk at the two deliberate bridges a coding agent still needs: a shared folder and a socket relay.
- **Both patched bugs are the same shape at two different bridges.** CWE-59 (link following) in virtio-fs and CWE-367 (TOCTOU) in the socket relay are formally different bug classes that reduce to the same sentence: the host trusted a guest-supplied reference the second time without re-checking it, and the guest controlled what changed in between.
- **`AV:L` means "the guest already ran code" — which is precisely the attacker this product is built to survive.** Don't read a local attack vector as a lesser bug when the product's entire purpose is containing a hostile or compromised guest.
- **The documented mitigation is "don't build the bridge," not "the bridge is now safe."** Read-only clone mode removes the write-back path structurally; it is the same lesson as avoiding the convenience bind mount in the container post, one layer up the isolation stack.
- **The fix shipped September 7; it only protects machines that pulled it.** A critical, locally-exploitable escape patched in a CLI tool depends on the developer updating — check what version of Docker Sandboxes you're actually running before trusting the boundary.
