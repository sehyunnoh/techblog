Igor Ostrovsky's "Gallery of Processor Cache Effects" is one of those 2010 blog posts that keeps resurfacing, and it came back to the Hacker News front page this week.[^1] Its first example is the one people remember. Take an array of 64 million integers. Loop A multiplies every element by 3. Loop B multiplies every 16th element by 3. Loop B does about 6% of the arithmetic, so it should finish in a fraction of the time. On his machine it took 78 ms against 80 ms for loop A.

That result is the whole point of the article: the CPU spends its time waiting for memory, not computing, so skipping work you never waited for saves nothing. Sixteen years is a long time in hardware, though. I rewrote the experiments in C and ran them on a 2026 laptop chip to see which of his claims still hold.

The cache cliffs held up fine. The headline did not. Loop B now finishes in well under half the time of loop A.

## A cache, in one paragraph

Main memory (RAM) is slow compared to the processor. To hide that, the CPU keeps small, fast copies of recently used data in **caches**, arranged in levels: L1 is the smallest and fastest, L2 is bigger and slower, L3 is bigger still and shared between cores. The CPU never copies a single number. It moves memory in **cache lines**, which are 64 bytes on x86, so reading one 4-byte integer also drags in the 15 neighbours that share its line. Everything below follows from those two facts.

## How I ran it

The machine is an Intel Core Ultra 7 258V, a laptop chip with 4 performance cores and 4 efficiency cores. I read the core types from Windows (`GetLogicalProcessorInformationEx`) and pinned every single-threaded test to a performance core. The code is C, compiled with gcc 16.2 at `-O2` with auto-vectorization turned off, so the loops stay scalar like the originals. Each number is the median of 5 to 9 runs. The full source is [one file you can download](/files/cache-effects-bench.c), and the methodology note at the bottom has the exact settings.[^2]

## Experiment 1: skipping elements

The loop is as plain as it sounds:

```c
for (size_t i = 0; i < N; i += k) a[i] *= 3;   // N = 64M ints, k = stride
```

Ostrovsky's claim is that the time stays flat for strides 1 through 16, then halves each time the stride doubles. Here is what I measured:

Stride 1 takes about 27 ms. Stride 16 takes about 10 ms. A second run of the same binary gave 26.6 and 10.0 ms, so the gap is not noise. In 2010 the two loops tied; today the 94% reduction in arithmetic removes a bit over 60% of the time.

Why? Stride 16 still touches every cache line in the array, so it moves the same amount of memory as stride 1, and 10 ms looks like roughly what this chip needs to do that. That makes 10 ms the memory floor. Stride 1 runs 16 times as many iterations on top of the same memory traffic, and on a machine this fast the extra instructions are no longer hidden.

I checked that explanation with a control. I ran the same 67 million multiply iterations over a 16 KB array that fits inside L1, so memory plays no part. That took 19.3 ms. In other words, roughly 70% of stride 1's 27 ms is plain instruction work, which the 2010 machine could bury under 80 ms of waiting and mine cannot. The memory system got fast enough that the arithmetic became visible again.

One more detail in the curve. Ostrovsky's data halves with every doubling of the stride after 16. Mine barely moves from stride 16 to 32 (10.1 to 8.9 ms) and only starts halving cleanly around stride 64. Intel's optimization manual covers the CPU's hardware prefetchers, and one of them, as summarized for earlier cores, treats memory as 128-byte pairs of lines and fetches the partner of any line you miss on.[^3] That would explain why touching every second line still pulls in every line. I did not confirm that this chip behaves that way, so treat it as a hypothesis that fits.

## Experiment 2: measuring the caches with a stopwatch

The second trick in the article is the one I find most fun. If you walk through arrays of growing size and time each access, the time jumps whenever the array stops fitting in a cache level. You can read the cache sizes off the graph without looking anything up.

I ran two versions. The first is Ostrovsky's pattern: touch one integer per cache line, in order, wrapping around inside the array. The second is a **pointer chase**: each 64-byte line holds the index of the next line to visit, arranged as one random cycle through the whole array. The CPU cannot guess where the next load goes until the previous one finishes, so every access pays full latency. A linked list scattered around the heap behaves the same way.

Both curves step up in the same places, so the 2010 technique still works. But look at the vertical scale. The sequential pattern only gets about 12 times slower between the smallest and largest array (0.22 to 2.6 ns). The pointer chase gets 116 times slower (1.1 to 127.9 ns). The hardware prefetcher notices the in-order walk, starts loading lines before the loop asks for them, and hides most of the memory latency. That is why a sequential benchmark understates how slow memory really is, and why I added the chase.

To pin the edges down, I reran the chase at sizes between the powers of two. The L1 cliff sits between 48 KB (1.10 ns) and 56 KB (2.63 ns), so the L1 data cache is 48 KB or close to it. The next step starts after 2 MB (5.1 ns) and is clearly under way by 3 MB (9.4 ns). Then latency climbs gradually from 12 MB (29 ns) to 32 MB (99 ns). Windows reports 12 MB of L3 for this chip, and that matches where the climb begins. The L3 is shared with the other cores and the rest of the system, so its edge is blurrier than L1's.

The practical reading is the pointer-chase column. A cache hit in L1 costs about 1 ns. A trip to main memory costs about 128 ns. When you walk a list of nodes scattered through memory, you can lose two orders of magnitude, and the sequential row shows how much of that an array layout buys back.

The threads never touch each other's variable, so you might expect no interference. But a core can only write to a cache line it holds exclusively, and when four cores take turns writing to one line, it bounces between them. This is called **false sharing**: the data is not shared, but the line is.

With one thread there is nothing to fight over, and both layouts take about 25 ms. At four threads the padded version still takes 27 ms while the packed one takes 268 ms, a factor of 10. Ostrovsky measured about 15 times (4.3 s against 0.28 s on his machine), so the penalty has shrunk a little, but it is nowhere near gone. The fix costs memory: each counter now occupies 64 bytes instead of 4.

## What I did not test, and where this can mislead

**One machine, one run of the whole suite.** This is a single laptop chip on Windows. I did not pin the clock speed or control the power plan, and a laptop can throttle. The repeated stride runs agreed within about 5%, but I did not repeat the entire suite across sessions, so small differences in the charts should not be over-read.

**Large-array latency includes address translation.** Programs address memory in 4 KB pages, and the CPU keeps a small table of recent page lookups. Past a few MB, my pointer chase misses that table as well as the data caches, so the 128 ns figure is cache plus page lookup. I did not separate the two, and huge pages would likely lower it.

**The prefetcher explanation is a guess.** The 128-byte-pair idea fits the stride data, but I never ran a test that would rule other explanations out.

**I skipped two of the seven original examples.** Cache associativity (example 5) and the odd counter-increment timings (example 7) need more care than this post had room for. I did run example 4, where one loop increments a single memory location twice and the other increments two locations. The 2010 result was a 2x gap. I measured 255 ms against 158 ms over 500 million iterations, a gap of about 1.6x, so the dependency chain still costs something but less than it did. I don't know why.

**Padding is not free.** Spreading counters 64 bytes apart multiplies their memory use by 16. It is worth it for a handful of hot per-thread counters and wasteful for a large array of them.

## Takeaways

- **Skipping work saves nothing only while memory is the bottleneck.** In 2010 an array loop was dominated by waiting. On a modern chip with a faster memory system, the instructions show up again, and skipping 15 of 16 elements removed over 60% of the time.
- **A pointer chase is the honest way to measure a cache.** It exposes real latency (about 1 ns in L1, about 128 ns in RAM here). A sequential walk hides most of that behind the prefetcher.
- **Layout still matters more than arithmetic.** Walking memory in order was around 50 times cheaper per access than hopping randomly through the same 256 MB.
- **False sharing is still a 10x penalty.** If threads write to separate variables that sit within 64 bytes of each other, give each variable its own cache line.
- **Re-measure old performance advice.** The qualitative lessons survived 16 years. The specific numbers, and one of the headline conclusions, did not.
