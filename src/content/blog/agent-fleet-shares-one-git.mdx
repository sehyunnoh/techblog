`git worktree add` finished in 132 milliseconds and wrote 44 files.

That is this blog's repository, and those 44 files are everything git tracks in it — 626 KB of Astro components, MDX posts and config. To actually build the site you need 23,199 more files weighing 405 MB, and `git worktree add` did not create a single one of them.

This matters because the worktree is now load-bearing infrastructure. The tool category that grew up around coding agents in 2026 — the ADE, agent development environment — is built on it. Orca, the one with the most traction, is explicit: "every task gets its own on-disk copy of the repo via `git worktree`. This is what makes parallel agents safe — they never step on each other's files."[^1] Run six agents, get six worktrees, no collisions.

For tracked files that is exactly true. This post is about the boundary: what `git worktree` isolates, what it quietly shares, and what the ADE has to build on top to cover the difference. The last part is where it gets interesting, because the standard fix for the gap is a symlink — and a symlink is the opposite of isolation.

## Where the term comes from, and what it is claiming

"Agent development environment" was coined by Letta for something else entirely: a workbench for building and debugging *agents themselves*, making context windows and reasoning visible.[^2] The coding world borrowed the acronym for a different object — a workspace for directing a fleet of agents that write code. Both meanings are in active use, which is worth knowing before you read a comparison page.

This post is about the second kind, and specifically about `stablyai/orca`: MIT-licensed, TypeScript, first commit 2026-03-17, 70,598 stars at the time of writing.[^3] Its repository topics include `worktrees` and `parallel-agents`, which is a fair summary of the architecture. Every claim below about Orca is from its source or its documentation at tag `v1.4.205`.

The claim under test is the one in the quote above: parallel agents are safe because they never step on each other's files.

## What a worktree actually splits

Git's own layout documentation states the rule without much ceremony:

> "When multiple working trees are used, most of files in `$GIT_DIR` are per-worktree with a few known exceptions. All files under _common_ however will be shared between all working trees."[^4]

The mechanism is a pointer. A linked worktree's `.git` is a file, not a directory, containing a path into the main repository:

```bash
$ git worktree add ../w1 -b agent1
$ cat ../w1/.git
gitdir: /tmp/r/.git/worktrees/w1

$ ls /tmp/r/.git/worktrees/w1
commondir  gitdir  HEAD  index  logs  ORIG_HEAD  refs

$ cat /tmp/r/.git/worktrees/w1/commondir
../..
```

Seven entries are private to the worktree. Everything else resolves back through `commondir` to the one shared repository. You can ask git directly which side of the line any given path falls on:

```bash
# run from inside ../w1
$ git rev-parse --git-path index
/tmp/r/.git/worktrees/w1/index     # private

$ git rev-parse --git-path objects
/tmp/r/.git/objects                # shared
$ git rev-parse --git-path config
/tmp/r/.git/config                 # shared
$ git rev-parse --git-path hooks
/tmp/r/.git/hooks                  # shared
```

The private index is the real win, and it is not a small one. Two agents can stage and commit simultaneously because `index.lock` is a different file for each of them. On a single shared checkout that is exactly the collision you cannot avoid.

## What stays shared, and what it costs

Three consequences follow from the right-hand column. Each one is reproducible in about thirty seconds.

**A branch belongs to one worktree.** Git refuses the second checkout outright:

```bash
$ git worktree add ../w2 agent1
Preparing worktree (checking out 'agent1')
fatal: 'agent1' is already used by worktree at '/tmp/w1'
```

The documentation confirms this is deliberate and that `--force` overrides it.[^5] In practice it shapes the workflow more than it looks. Orca's own "race three agents on the same task" recipe instructs you to create three worktrees named `fix-bug`, `fix-bug-2`, `fix-bug-3` — three branches, because three agents cannot share one.[^6] A supervisor-and-worker split on a single branch is not expressible at this layer.

**Hooks are global.** Install a `pre-commit` hook in the main checkout and it fires everywhere:

```bash
# written once, in the main checkout
$ printf '#!/bin/sh\necho "[hook fired in $(git rev-parse --show-toplevel)]" >&2\n' \
    > .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit

# committed from a different agent's worktree
$ cd ../w2 && git commit -m "from agent2"
[hook fired in /tmp/w2]
[agent2 879b535] from agent2
```

This is the sharp edge. An agent that runs `npm install` in a repository using husky, lefthook or pre-commit rewrites the commit path for every other agent in the fleet, mid-run, with no signal that anything changed. The same applies to `.git/config`: remotes, aliases and `core.*` settings are one file. Git does offer per-worktree config behind `extensions.worktreeConfig`, but it is opt-in and the documentation scopes it narrowly — `core.worktree`, `core.bare`, `core.sparseCheckout`.[^5]

**Ref updates contend.** Branch locks live in the common directory, so concurrent `fetch` or `commit` across worktrees serialises on the same files:

```bash
$ git update-ref refs/heads/agent1 HEAD
fatal: update_ref failed for ref 'refs/heads/agent1':
  cannot lock ref 'refs/heads/agent1': Unable to create
  '/tmp/r/.git/refs/heads/agent1.lock': File exists.
```

At six agents this is usually invisible — lock windows are milliseconds. It stops being invisible when something long-running holds one: a `git gc` triggered by one agent's commit rewrites the shared object store and packed-refs for all of them.

None of this is a bug. It is the design: a worktree is a second *working tree*, not a second repository. The word is doing exactly what it says.

Orca's documentation states the gap plainly rather than papering over it:

> "A brand-new worktree is a clean checkout. Dependencies, caches, and local secrets that live in gitignored paths are missing until you recreate them."[^1]

It then offers three ways to fill it: per-user shared paths, `worktree.sharedDirectories` in a checked-in `orca.yaml`, and a `.worktreeinclude` file at the repository root. What makes this worth reading closely is that the three are not variations on one idea. They implement two *opposed* policies, and the source says why:

```ts
// 'link': symlink when APFS clone is unavailable (user-configured shared paths).
// 'copy': real copy when APFS clone is unavailable (.worktreeinclude paths, which
// are per-worktree copies by cross-tool convention — edits must not leak back).
// 'share': always symlink (orca.yaml sharedDirectories). An APFS clone would give
// each worktree an independent node_modules, defeating one-install-serves-all.
```

That is from `worktree-symlinks.ts`.[^7] Read the last comment again. For `.env` and local editor config the requirement is that **edits must not leak back** — each worktree owns its copy. For `node_modules` the requirement is the exact opposite: an independent copy per worktree would *defeat* the goal, which is stated as **one-install-serves-all**.

There is a size guard on the copy path, and its comment is candid about what drove it: a repository that lists `node_modules` in `.worktreeinclude` "freezes worktree creation for minutes behind an inline copy." The limits are 2 GiB and 50,000 entries, cumulative across the run, and an over-budget entry is skipped with a warning rather than failing the create.[^8]

Worth checking against your own repository rather than assuming. This blog's `node_modules` — 23,199 entries, 405 MB — sits under *both* limits. Listing it in `.worktreeinclude` here would produce a genuine per-worktree copy; on a repository a little larger the same line silently does nothing, and the difference surfaces as a build failure in one worktree and not another.

## The share mode is the un-isolation

The interesting mode is `share`, because it is the one you will reach for. Nobody wants to pay 405 MB and a full install per agent. So `node_modules` gets symlinked — a directory junction on Windows, since Orca's source notes that a plain symlink there needs Developer Mode or admin and otherwise fails with `EPERM`.[^7]

Here is what that buys, measured:

```bash
# node_modules shared into two worktrees, Orca 'share' mode
$ cmd //c mklink //J w1/node_modules "$PWD/node_modules"
$ cmd //c mklink //J w2/node_modules "$PWD/node_modules"

# agent1 upgrades a dependency, inside its own isolated worktree
$ echo 'v2-installed-by-agent1' > ../w1/node_modules/left-pad/version

  agent2 now reads : v2-installed-by-agent1
  primary now reads: v2-installed-by-agent1
  agent2 'git status' changed files: 0
```

Four lines, and they contain the whole problem. agent1 changed a build input. agent2's build inputs changed with it. And `git status` in agent2's worktree reports a clean tree, because git was never looking at that directory in the first place.

The realistic version of this is not a contrived `echo`. It is an agent handed a task like "upgrade the router to v7 and make the tests pass." That agent will run a package manager. The lockfile it edits is tracked, so the lockfile is isolated. The installed tree it rewrites is shared, so it is not. The two now disagree — per worktree, invisibly — and the first symptom is another agent's test suite failing for a reason that is nowhere in its own diff.

This is not a flaw in Orca specifically. It is the only available trade for a category built on `git worktree`: you can have one install serving the fleet, or you can have isolation, and the mechanism cannot give you both. What Orca does do, to its credit, is put the choice in the repository as checked-in configuration rather than burying it — `sharedDirectories` is a decision someone made on purpose, visible in code review.

## Where the boundary actually belongs

The useful question is not whether worktrees are good. It is which layer your tasks need, given what they do.

The practical test is a single question: **does the task run a package manager, bind a port, or write to a database?**

If the answer is no — review a diff, write documentation, refactor within existing dependencies, add tests to an existing suite — worktrees are the right layer and the 132 ms matters. Six of those in parallel is genuinely the cheapest isolation available, and the shared object store is a feature: every agent's commits are immediately readable from every other worktree without a fetch.

If the answer is yes for even one agent in the fleet, the worktree is not the boundary you think it is. A dependency upgrade, a migration that touches a local database, a dev server on port 3000 — each of those escapes the worktree, and the escape is silent because git does not track the thing that escaped.

The uncomfortable part is that these two categories look identical when you queue the work. "Fix the failing test" is in the first category until the fix turns out to require a version bump.

## Takeaways

- **A worktree isolates the working tree, not the repository.** Objects, refs, config and hooks live in the common directory and belong to the whole fleet. Verify with `git rev-parse --git-path <name>` rather than assuming.
- **Hooks are the sharpest shared edge.** One agent running `npm install` in a husky repository rewrites the commit path for every other agent, mid-run, with no signal.
- **One branch, one worktree.** Git refuses the second checkout. Any workflow needing two agents on one branch has to be expressed some other way.
- **The isolation guarantee stops at `.gitignore`.** On this repository that is 44 files isolated and 23,199 not — a 647× gap by size, and the larger side is the side builds depend on.[^9]
- **`share` mode is not isolation, and is not pretending to be.** Orca's own source says a per-worktree `node_modules` would defeat one-install-serves-all. That is a deliberate trade, and it means a dependency change by one agent is a dependency change for all of them.
- **Match the layer to the task.** Package manager, port, or database in play means the boundary has to move up to a container. Otherwise worktrees are the cheapest thing that works, and 132 ms is hard to beat.
- **Check the copy budget against your own tree.** 2 GiB and 50,000 entries, and going over is a skipped path with a warning — not an error you will notice at create time.
