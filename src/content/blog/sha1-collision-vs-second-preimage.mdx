Git identifies every file, folder and commit in a repository by a hash: a short string computed from that object's exact content. Change one character anywhere in the content and the hash comes out completely different. For twenty years that hash has been produced by an algorithm called SHA-1. Git 3.0, expected by the end of 2026, will make a different algorithm, SHA-256, the default for every new repository, and the change reaches further than a configuration flag: submodules, signed commits, and any tool that quietly assumed a Git hash is exactly 40 characters long.[^1][^2]

Scott Chacon, a GitHub co-founder, the author of the project's own reference book (Pro Git), and now the founder of GitButler, thinks the migration is a mistake, not because the idea is bad, but because it fixes the wrong problem.[^3] His argument turns on a distinction that is easy to miss unless you look closely at what has actually been broken in SHA-1, and what has not.

## What a hash actually buys Git

If "hash function" is new to you: it is a piece of math that takes any amount of data (a single line, or an entire codebase) and produces a fixed-length string that acts like a fingerprint for that exact content. Feed it the same bytes twice and the fingerprint comes out identical every time. Change even one byte and the fingerprint comes out completely different, in a way nobody can predict in advance.

Git uses this fingerprint for everything. Every file's content, every folder listing, every commit becomes an "object," and that object's hash is its name. There is no separate numbering system and no auto-incrementing ID sitting behind the scenes. Two files anywhere in a repository's history with identical content get the identical hash, which is also how Git avoids storing the same content twice. When you type a command like `git show 1a2b3c4`, you are asking Git to find the object whose fingerprint starts with those characters.

That fingerprint has been produced by SHA-1 since Git's very first commit in 2005. SHA-256 is a newer algorithm from the same family that produces a longer fingerprint: 256 bits instead of 160, written out as 64 hexadecimal characters instead of 40.

## The ID itself gets longer, and some things stop working

I built two throwaway repositories to see this directly rather than take it on faith: one using the current default, one using Git's SHA-256 mode, which has existed as an opt-in feature since 2020.[^2] Committing the same one-line file into each produces hashes of very different shapes.

Forty characters versus sixty-four does not sound dramatic on its own, but a huge amount of software quietly assumes a Git hash is exactly 40 characters: commit-linking tools, log parsers, URL patterns, regular expressions copied from a decade-old Stack Overflow answer. Git's own documentation is direct about the bigger structural cost: "SHA-256 repositories cannot be read by older versions of Git," full stop.[^2] A repository converted to the new format cannot simply be opened by whatever Git happens to already be installed somewhere.

Both failures were immediate and unambiguous, which is the right behavior: Git refuses to silently mix the two formats rather than producing something subtly broken. But "refuses immediately" is still a real cost if the two repositories involved are, say, a large company's main codebase and a vendor's dependency that hasn't converted yet. A submodule relationship or a fetch that worked yesterday stops working the day one side upgrades its hash format and the other hasn't.

## Four named attacks, and what none of them do

Here is the part of the story that motivated the switch in the first place. Git's own breaking-changes documentation lists four published attacks against SHA-1 by name, in order, along with roughly how much computation each one took:[^5]

The jump between 2017 and 2019 looks like attacks getting harder, not easier, and that is real: SHAttered in 2017 was an "identical-prefix" collision, where both colliding files have to start with the same bytes, which is comparatively cheap. The 2019 result was the first "chosen-prefix" collision, where the attacker can pick two files that look completely different from the start and still land on the same hash, a much more dangerous capability that initially cost more to pull off. Shambles in 2020 brought that more dangerous attack back down to roughly the same cost as SHAttered, at an estimated $45,000 using rented cloud GPUs, and the researchers used it to forge PGP identity certificates as a demonstration.[^6]

All four, though, are collision attacks. That means the attacker gets to construct both documents, picking whatever content makes the hashes line up. What none of these attacks does is take a hash someone else already published, like the commit hash at the top of a pull request you are about to approve, and produce a different, malicious piece of content that hashes to that exact same value. That second kind of attack is called a second-preimage attack, and no practical second-preimage attack against SHA-1 has ever been published.

## Where Git's real trust boundary sits

This is the center of Chacon's argument: Git almost never asks you to trust a piece of code purely because its hash matches some number you were told in advance. You decide to trust code by deciding to trust a source, a GitHub account behind an HTTPS connection, a colleague's machine over SSH, a release tarball signed with someone's GPG key, and the hash's job from there is narrower than it sounds: catching accidental corruption and letting Git tell whether two pieces of content are the same, not standing alone as your only line of defense against an adversary.[^3]

That is not an argument that SHA-1 is fine forever. NIST, the U.S. agency that sets federal cryptography standards, deprecated SHA-1 for digital signatures back in 2011 and plans to remove it from its standards entirely by the end of 2030, and Git's own documentation cites that institutional pressure alongside the research attacks as a reason to move.[^1][^7] Chacon's objection is narrower: that the specific, disruptive, default-breaking shape of this particular migration is a poor match for a threat that, so far, has only ever let researchers build two documents from scratch that agree with each other, not forge a replacement for something you already reviewed and trust.

## Trade-offs worth noticing

- Git already hardened its SHA-1 implementation against the SHAttered attack specifically back in version 2.13 (2017), without changing the default hash or breaking anything.[^1] The new migration is aimed at attacks that have not been demonstrated yet, not at closing a hole that is currently open.
- The costs are concrete and itemized in Git's own documentation: submodules, GPG signatures, `git notes`, object borrowing between repositories ("alternates"), and shallow clones all need explicit handling across the two formats, and some combinations (like borrowing objects from a SHA-1 repository into a SHA-256 one) are not supported at all.[^2]
- Git 3.0 bundles this change together with unrelated breaking changes shipping in the same release: a new on-disk format for branch references called "reftable," a change to the default branch name, and a new requirement that Git be built with a Rust toolchain available.[^1] None of those are about hashing, but they all land on users at the same time.
- There are two separate reasons being used to justify one migration: a compliance-driven one (NIST's deprecation timeline) and a research-driven one (the four attacks above). They point in the same direction, but they are not the same argument, and conflating them makes the change look more urgent against real-world attackers than the second one alone would support.

## Takeaways

- **A Git hash's job is narrower than "security."** It identifies content and lets Git detect accidental corruption and avoid duplicate storage. Whether you trust that content in the first place is a decision Git mostly leaves to how you connect to a source, not to the hash itself.
- **Every published attack on SHA-1 so far is a collision attack, not a second-preimage attack.** That distinction decides whether the danger is "an attacker can build two documents that match each other" (demonstrated, four times) or "an attacker can replace a document you already trust without changing its hash" (never demonstrated).
- **Breaking changes compound when they ship together.** Git 3.0's hash default, reftable format, branch naming, and Rust requirement are four independent changes bundled into one release, which makes the total migration cost harder to reason about than any single piece of it.
- **Compliance deadlines and demonstrated attacks are different kinds of pressure.** NIST's 2030 SHA-1 removal date and the four research attacks both push toward SHA-256, but only one of them depends on what an actual attacker can currently do to a Git repository.
- **Testing the compatibility claims directly took minutes and confirmed them exactly.** Git's documentation said submodules and fetches would fail across hash formats; they failed with the precise error messages the documentation implies, on the first try.
