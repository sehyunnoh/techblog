Ten processes ran `git update-ref refs/heads/integration <sha>` at the same instant, against the same ref, in the same repository. All ten exited 0. Git told every one of them the write had succeeded.

Only one of the ten survived. Check the ref afterward and it points to whichever process happened to finish last. The other nine, each one a clean, zero-exit-code success, are gone. Not logged as an error. Not flagged as a conflict. Just absent, as if they had never run.

That's the actual result behind this post, and it's relevant right now because of a tool that hit GeekNews this week: [`max-sixty/worktrunk`](https://github.com/max-sixty/worktrunk), a CLI for running several coding agents in parallel git worktrees. It's four months old, past 8,400 stars, and its signature command, `wt merge`, does precisely the operation that produced the race above: it folds a finished agent's branch into a trunk branch from a worktree that never checked that branch out.[^1]

[A previous post on this blog](/posts/agent-fleet-shares-one-git) measured what `git worktree` actually isolates and found the boundary holds for the files an agent's own worktree owns: a private index, a private `HEAD`, a private staging area. Agents commit in parallel without touching each other's work, and the numbers below confirm that again. What that post didn't cover is the step after committing: folding several agents' branches back into one. That's a different operation, with a different failure mode, and it's the one worktrunk automates.

## Separate branches really are safe to commit to

Five worktrees, five branches, twenty commits each, fired at the same time from separate processes on this machine (git 2.55.0.windows.4, a scratch repository built for this test):[^5]

Zero commit failures in either run. This is the expected result, and it's worth stating plainly why: each agent's branch is its own file under `refs/heads/`, and each worktree has its own `index.lock`. There's no shared resource for two commits on two different branches to fight over. The 3.27x speedup is close to what five independent processes should buy you, minus the overhead of spawning a `git` process per commit on Windows.

This is the case worktrunk's `wt switch` and everyday agent commits live in, and it holds up. The trouble starts one step later.

## The moment two agents target the same branch

`wt merge` exists to take a feature branch and land it on a target branch, whether that's `main` or an integration branch shared by a fleet of agents.[^1] That target branch typically isn't checked out in the worktree doing the merging, so this isn't the familiar `git merge` you run inside a checkout. It's closer to a `git push` into a bare-style destination: read the target's current tip, verify the incoming commits build on it, then move the target ref forward.

To see what happens when several agents try to do that at once, I pointed ten worktrees at the same non-checked-out branch and had all ten run the plainest possible ref update simultaneously:

```bash
$ git update-ref refs/heads/integration <this-agent's-sha>
```

Ten out of ten calls returned 0. Fifty out of fifty did the same when I reran the test with forty more worktrees. In both runs, exactly one write is left standing afterward; the rest are indistinguishable, from the caller's point of view, from having never happened.

## Git's own retry is what's hiding this

This isn't a Windows quirk or a fluke of my test rig. It's a documented setting doing exactly what it's documented to do. `core.filesRefLockTimeout` controls how long `git update-ref` keeps retrying when the ref's lock file is already held, and it defaults to 100 milliseconds of retrying before giving up.[^2] That's long enough that ten or even fifty short-lived `git update-ref` calls, launched close together, each eventually get their turn at the lock and each report success, while quietly clobbering whatever the previous holder wrote.

Turn the retry off and the same race stops hiding:

```bash
$ git -c core.filesRefLockTimeout=0 update-ref refs/heads/integration <sha>
fatal: update_ref failed for ref 'refs/heads/integration':
  cannot lock ref 'refs/heads/integration': Unable to create
  '.git/refs/heads/integration.lock': File exists.

Another git process seems to be running in this repository, or
the lock file may be stale
```

With retrying disabled, the ten-agent run produced 1 explicit failure out of 10; the fifty-agent run produced 1 out of 50. The collision rate didn't scale with agent count in this test, because the actual critical section, the read, verify, write and rename around the lock file, is short. What scales with agent count isn't the failure rate, it's the number of successful calls whose result you can no longer trust, because "succeeded" and "survived" turned out to be two different claims.

## What worktrunk's merge command actually does

The reason to look at worktrunk specifically, rather than just at `git update-ref`, is that its author already ran into this and built around it. The function behind `wt merge`, `advance_target`, doesn't call the two-argument form I used above. It calls the three-argument one:

```rust
// src/commands/worktree/push.rs, advance_target()
repo.run_command(&[
    "update-ref",
    "-m",
    reflog_message,
    &target_ref,
    new_sha,
    old_sha,
])
```

That third argument changes the operation's meaning entirely. Git's own documentation draws the line precisely: with two arguments, `update-ref` "stores the new object name in the ref"; with three, it stores the new value "after verifying that the current value of the ref matches" the third argument, and refuses otherwise.[^2] That's a compare-and-swap. `old_sha` is the target's tip as this agent last saw it. If nothing else has moved the branch in the meantime, the write goes through. If another agent's merge landed first, the check fails, loudly, with a nonzero exit code and a message an agent or a human can act on, instead of the silent overwrite from the section above.[^3]

## Even a compare-and-swap has a seam

Worktrunk's own test suite is candid that the three-argument fix doesn't close the gap all the way. One test, `advance_target_carries_dirty_files_and_refuses_atomically`, builds an incoming merge that would overwrite a file with local, uncommitted edits still sitting in the target worktree.[^4] The compare-and-swap on the ref succeeds fine; the problem shows up one step later, syncing that worktree's files to match the new tip. When the incoming change and the local edit touch the same file, `advance_target` detects it and rolls the ref update back atomically, rather than leaving the branch pointer ahead of a working tree it can't safely update.[^4] When the local edits don't overlap with what the merge changes, it carries the local file untouched and lets the ref move.

The authors go further and document, in the source itself, a second and narrower seam: the compare-and-swap covers the ref update, but not the moment right after it, while the target worktree's files are being synced to match. A commit landing in that specific window can be pushed successfully and still get its content reverted by the sync that follows, while staying present in the branch's history. Worktrunk's response isn't to claim this can't happen. It re-reads the ref after the sync and, if it no longer matches what was just pushed, prints a warning rather than pretending nothing occurred.[^4]

None of this is a defect specific to worktrunk. It's what's actually involved in making "several independent processes update one shared pointer" safe, and most of the pieces are invisible until you go looking, the way `core.filesRefLockTimeout` was invisible until I turned it off.

## Takeaways

- **A successful exit code from `git update-ref` doesn't mean your write survived.** With the default 100 ms lock retry, ten or fifty concurrent updates to the same ref can all return 0 while only one of them actually sticks.
- **The default retry isn't a bug fix, it's a smoothing effect.** `core.filesRefLockTimeout` defaults to 100 ms specifically to make brief lock contention invisible.[^2] That's the right choice for a human occasionally racing a hook. It's the wrong one to lean on when N automated agents are all writing to the same branch.
- **Two-argument `update-ref`, or an unqualified force-push, is a last-write-wins operation.** If your own tooling folds multiple agents' work into a shared branch this way, silent lost updates are the expected outcome under load, not an edge case.
- **Three-argument `update-ref` turns a silent loss into a loud, actionable failure.** That's the whole fix: verify the old value, fail if it moved. Worktrunk's `advance_target` does exactly this, and cites the ref's own compare-and-swap semantics from git itself rather than inventing a lock of its own.[^3]
- **Compare-and-swap on the ref doesn't cover everything downstream of it.** The working tree still has to be synced to the new tip, and worktrunk's own comments and tests acknowledge that window rather than hiding it: overlapping local edits cause an atomic rollback, and a race in the sync step produces a warning instead of a false "all clear."
